# AI 平台部署与凭据说明

## 1. 平台角色

本服务部署方是平台管理方。`admin` 账号用于配置模型渠道、企业账号、充值额度、项目 Key、用量和审计。

外部企业使用独立的普通用户账号登录，不使用 `admin`。业务项目只保存平台颁发的项目 Key，并通过服务端调用平台 API。

```text
平台管理员 -> New API 管理后台 -> 企业账号 / 额度 / 项目 Key / 模型渠道
业务项目后端 -> 项目接入中转层 -> /v1/* -> New API -> 合法授权的上游模型 API
```

项目接入中转层只接收项目侧服务端凭证和业务企业标识，不向业务项目返回内部 New API Key。每个业务企业必须绑定独立的 New API 普通用户账户和余额。

## 2. 本地 POC 启动

项目目录：`<PROJECT_ROOT>`

当前 POC 的 `new-api` 使用 `Dockerfile.local` 复用官方运行层，并注入本地源码构建的 `new-api` 二进制；二进制被 `.gitignore` 忽略，不进入提交。源码变更后先在项目根目录执行：

```bash
cd <PROJECT_ROOT>/web
bun install --frozen-lockfile
bun run build
cd ..
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o new-api ./
```

```bash
cd <PROJECT_ROOT>
docker compose up -d
docker compose ps
curl --noproxy '*' http://127.0.0.1:3000/api/status
```

浏览器访问：<http://127.0.0.1:3000>

当前 POC 已在 `docker-compose.yml` 中将关键请求限流设置为每 60 秒 100 次，避免本地多账号登录、退出和 Session 刷新共用默认的 20 分钟窗口。生产部署前应根据真实入口、反向代理和账号规模重新评估，不建议直接关闭限流。

首次启动时访问 <http://127.0.0.1:3000/setup>，按向导完成：

1. 检查数据库；
2. 设置管理员用户名和密码；
3. 选择 `External operations`（企业/多用户模式）；
4. 完成初始化。

### 启动项目接入中转层

中转层是本地 POC 的独立 HTTPS 服务，监听 `https://127.0.0.1:3001`，只转发 `/v1/*`。先按 `bridge/.env.hedezhongcheng.example` 创建本机忽略配置 `bridge/.env.hedezhongcheng.local`，并在模板指定的证书目录中放置 `fullchain.pem` 和 `privkey.pem`，再启动：

```bash
cd <PROJECT_ROOT>
docker compose --env-file bridge/.env.hedezhongcheng.local --profile bridge up -d --build project-bridge
curl --cacert ./bridge/certs/hedezhongcheng/fullchain.pem --noproxy '*' https://localhost:3001/health/ready
```

### edu-training 独立 bridge

`edu-training` 不使用 `hedezhongcheng` 的 `bridge/.env.hedezhongcheng.local`。复制专用模板并填写平台管理员签发的项目凭证、各学校对应的内部 Key，并在模板指定目录中放置 `fullchain.pem` 和 `privkey.pem`：

```bash
cp bridge/.env.edu-training.example bridge/.env.edu-training.local
docker compose --env-file bridge/.env.edu-training.local --profile bridge up -d --build edu-training-project-bridge
curl --cacert ./bridge/certs/edu-training/fullchain.pem --noproxy '*' https://localhost:3002/health/ready
```

该实例使用宿主机端口 `3002`，容器内仍监听 `3001`。`edu-training` 后端的 `BRIDGE_BASE_URL` 应使用 HTTPS，并信任该证书颁发链；原 `project-bridge` 和 `bridge/.env.hedezhongcheng.local` 保持不变。

`AI_BRIDGE_ENTERPRISE_TOKENS` 每行一个 `企业标识=内部 New API Key`。HZC A-02 使用 `hdzc-shared` 映射到共用商户 Key；每个招聘企业和其他项目企业使用各自标识与独立计费账户。真实 Key 只通过 Secret 或本机忽略配置注入，不写入文档或提交。

### 生产 HZC Bridge 入口

HZC 后端正式接入时，使用服务器受控配置中记录的内网 HTTPS Bridge 地址。生产 Compose 不发布 Bridge 的宿主机端口。生产 Bridge 已限定为只监听 HZC Docker 网络的固定地址，该绑定与内网 HTTPS 已在生产生效。防火墙脚本会核对 Compose 地址、监听地址和目标地址，任一失配时拒绝应用规则；防火墙规则及其持久化 systemd 单元尚未安装到生产服务器，Bridge 自身的 `ai-platform-bridge.service` 已安装并启用。仓库中的 Bridge 服务单元是未部署候选，并硬依赖防火墙单元；替换生产单元前，必须先安装并验证防火墙单元。内部域名和地址不写入公开状态文档。

Bridge 使用独立证书。不要把公共 AI 门户正在使用的通配符私钥挂载给 Bridge。证书由 Certbot 的 DNS-01 验证签发；这个验证只需要临时 TXT 记录，不需要公网 A 记录。Certbot 部署钩子只更新 Bridge 的证书副本，并在 Bridge 已运行时重启 Bridge。

生产 Compose 同时设置 `AI_BRIDGE_TLS_CERT_FILE` 和 `AI_BRIDGE_TLS_KEY_FILE`，并以只读方式挂载证书。Bridge 在缺少任一变量、证书无效或不可读时拒绝启动，不会回退到 HTTP；因此服务必须使用有效且可读的证书和私钥。

Bridge 容器的重启策略为 `no`。`ai-platform-bridge.service` 前台运行 Compose，并在 Bridge 容器退出时重启。该单元排在防火墙单元之后；Docker 重启时，systemd 按依赖顺序先恢复防火墙规则，再启动 Bridge。手动停止后，使用 `systemctl restart ai-platform-bridge.service` 恢复。`systemctl status` 显示 `active` 只表示 Compose 进程仍在运行，不代表容器已通过健康检查；还要检查容器状态并访问 readiness。Bridge 的 HTTPS 最低使用 TLS 1.2。HZC 容器已通过证书链和域名校验访问 readiness；该结果只证明内网 HTTPS 和进程可用，不代表项目凭证、商户 Key、共享余额或模型调用已验收。

生产 Compose 已配置 Bridge→New API 的内网 HTTPS 上游。证书链、主机名及 TLS 1.2/1.3 探针已通过；该结果不代表共享余额、模型推理或扣费业务已验收。

生产 Compose 在保留 New API 现有 `3000` HTTP 监听的同时，增加供 AI 平台 Docker 网络访问的 `3001` HTTPS 监听；`3001` 不映射到宿主机。门户现有 Nginx 和 `3000` 监听保持不变。

监听地址、证书和私钥分别由 `AI_PLATFORM_INTERNAL_TLS_LISTEN_ADDR`、`AI_PLATFORM_INTERNAL_TLS_CERT_FILE`、`AI_PLATFORM_INTERNAL_TLS_KEY_FILE` 设置。三个变量全部未设置时，New API 不启动内部 TLS 监听；只提供监听地址或只设置一项证书变量时，启动会失败；证书无法加载时，启动也会失败。证书和私钥有效时，未设置监听地址会使用 `:3001`。本地候选 Compose 设置三个变量，把宿主机证书目录放在 New API 可写数据目录之外，并以只读方式挂载到 `/run/ai-platform/new-api-tls`；Certbot 续期钩子也写入该独立目录。此路径调整尚未部署；发布前须迁移现有证书副本，并验证权限、证书链和服务启动。不要把 AI 门户通配符私钥复用给 New API。内部 HTTPS 使用 TLS 1.2 或更高版本。

生产运行状态、凭证核验结果和待完成的业务验收，以 [`生产对照核验.md`](../deploy/production/生产对照核验.md) 和 [`生产服务器部署状态.json`](./生产服务器部署状态.json) 为准。

### 配置第一版 SSO

`AI_SSO_PROJECTS` 每行一个 `项目标识|项目 SSO 客户端密钥|企业标识|精确回调地址`。HTTP 回调仅允许本机回环地址，正式环境使用 HTTPS；项目密钥只通过 Secret 或本机忽略配置注入。授权入口为 `/api/sso/authorize`，项目后端使用 `/api/sso/token` 兑换一次性授权码，兑换后由项目自己建立 HttpOnly 会话。

## 3. 管理员凭据规则

- 当前 POC 管理员用户名为 `admin`。
- 管理员密码是在首次初始化页面手动设置的，不在 Docker Compose、代码、日志或数据库中保存明文。
- 密码不应写入 Git、项目文档或聊天记录；部署完成后应保存到团队密码管理器。
- 因此，密码不能“查出来”；忘记密码时应执行重置，而不是搜索文件或日志。

### 忘记密码

- 已有登录会话：进入个人资料中的密码安全设置，直接修改密码。
- 配置了邮箱和 SMTP：在登录页使用“忘记密码”。
- 当前本地 POC 未配置 SMTP；如果没有任何已登录会话，需要由平台负责人确认后执行受控重置。

## 4. 企业账号使用

1. 管理员在“用户管理”创建企业账号。
2. 管理员通过“人工调整额度”或“兑换码”给企业增加额度。
3. 企业账号登录后创建项目 Key；不同业务项目使用不同 Key。
4. 业务项目后端使用项目凭证、`X-AI-Project-Id`、`X-AI-Enterprise-Id` 和 `X-AI-Feature` 经中转层调用 `/v1/chat/completions` 等兼容接口。
5. 企业和项目的用量、余额、成本及请求日志在平台侧审计；会话、业务数据、Flint 和图形展示由业务项目自己实现。

当前 POC 已创建 `enterprise-poc` 测试账号和 `project-hedezhongcheng-poc` 项目 Key；中转层映射仍是配置驱动，动态项目登记、企业绑定和平台侧审计管理尚未建设。

## 5. 生产部署前门禁

- 轮换 Compose 中的数据库、Redis 和会话密钥，不沿用本地默认值。
- 固定镜像版本或摘要，不使用未固定的 `latest`。
- Bridge 必须同时配置 `AI_BRIDGE_TLS_CERT_FILE` 和 `AI_BRIDGE_TLS_KEY_FILE`；证书目录只读挂载，且使用独立证书与密钥。
- 应用 Bridge 防火墙规则前，脚本会读取 Compose 所用外部 Docker 网络的实际 IPv4 子网，并验证固定 Bridge 地址属于该子网；网络子网不唯一或地址不匹配时，脚本拒绝应用规则。
- PostgreSQL 备份脚本读取 `/data/ai-platform/production.env` 和 `/data/ai-platform/bridge-compose.yml`；这两个文件必须存在，且需与运行中的服务配置一致。
- 备份 service 失败后每 5 分钟重试；6 小时内最多启动 4 次（包括首次）。仍失败时，检查 `systemctl status ai-platform-backup.service` 和 `journalctl -u ai-platform-backup.service` 并人工处理；当前没有失败通知配置。
- 对外 WebSocket 接口使用 HTTPS/WSS；AI 门户 Nginx 会转发 `Upgrade` 和 `Connection` 请求头。
- 配置 HTTPS、可信域名、SMTP、备份和日志保留策略。
- 仅接入合法取得并允许当前服务场景使用的官方模型 API。
- 按 AGPLv3 保留许可证、署名、原项目链接，并为修改后的网络服务提供对应源码。
